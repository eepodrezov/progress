# Доменная модель и бизнес-правила (Этап 1)

Цель этапа: зафиксировать “единый источник правды” по терминам/статусам и правилам, чтобы расчет дат и отчеты не ломали данные.

## Release

### Статусы релиза
- `draft`: черновик (можно менять параметры, состав КТ, задачи, стеки)
- `active`: активный релиз (исполняем КТ)
- `done`: релиз завершен
- `cancelled`: отменен

На текущей реализации статус хранится в БД, но UI/процессы можно добавить позже.

## Milestones (контрольные точки)

### Поля дат
- `suggested_at`: дата, предложенная алгоритмом (результат расчета)
- `planned_at`: дата, подтвержденная человеком (может отличаться от suggested)
- `actual_at`: фактическое время прохождения

### Статусы КТ
- `planned`: запланирована (не пройдена)
- `done`: пройдена
- `blocked`: заблокирована/остановлена
- `skipped`: пропущена

## Правила качества данных

### Обязательный комментарий
- если `status = blocked` → `delay_reason` обязателен (**реализовано в API**)

### Просрочка (для будущих отчетов/аналитики)
Минимальная трактовка задержки:
- если есть `planned_at` и `actual_at` и \(actual\_at > planned\_at\) → считается задержкой

Замечание: на следующих этапах можно уточнить, что считается базой сравнения (planned vs suggested).

## Данные для расчета длительности

### Задачи релиза
- вводятся в часах (`release_tasks.hours`)
- в расчет будет использоваться сумма часов

### Стеки
- выбранные стеки релиза (`release_stacks`)
- в расчет будет использоваться count/перечень стеков (по правилам/коэффициентам)

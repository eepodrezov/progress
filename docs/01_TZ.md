# Техническое задание (ТЗ)

Проект: **Информационная система контроля сроков контрольных точек релизного цикла команды**  
Формат: **Web-приложение (React / Next.js)**  
Цель: **планирование, контроль прохождения и аналитика по контрольным точкам релизов**

## 1. Назначение и цели системы

**Назначение**: вести релизы команды, формировать план контрольных точек (milestones) от даты релиза, фиксировать факт прохождения и задержки, формировать отчеты и аналитику.

**Цели**:
- снизить ручные ошибки при планировании дат этапов
- обеспечить прозрачный статус по незавершенным релизам
- собрать ретроспективные данные по задержкам и причинам

## 2. Основные сущности и термины

- **Релиз**: единица планирования и контроля (имеет дату релиза, набор задач, набор контрольных точек)
- **Контрольная точка (КТ)**: этап релизного цикла, для которого планируется дата и фиксируется факт прохождения
- **Задачи релиза**: вводятся в часах; используются для приблизительного расчета длительности этапов
- **Стеки**: перечень участвующих технологических направлений; влияет на оценку интервалов этапов
- **Календарь рабочих дней команды**: используется при расчете предлагаемых дат контрольных точек

## 3. Роли и пользователи

- **Пользователь системы**: создает релизы, выбирает контрольные точки, редактирует даты, вручную отмечает прохождение, формирует отчеты/аналитику
- **Администратор (опционально)**: управляет справочниками (набор КТ “по умолчанию”, интервалы этапов, календарь рабочих дней, список стеков)

## 4. Функциональные требования

### 4.1. Создание нового релиза

При создании релиза задаются (минимально):
- название/идентификатор релиза
- дата релиза
- список задач релиза (суммарно в часах или перечнем задач с часами)
- количество/список участвующих стеков

### 4.2. Выбор набора контрольных точек

При создании релиза пользователь выбирает набор необходимых контрольных точек:
- по умолчанию выбран принцип “базово все”
- пользователь снимает (убирает) ненужные контрольные точки

### 4.3. Запрос и расчет дат контрольных точек

После задания даты релиза система формирует предлагаемые даты КТ:
- расчет от даты релиза
- учитываются:
  - рабочие дни команды (календарь)
  - сохраненные интервалы этапов (КТ)
  - рост интервалов по сумме часов задач
  - зависимость интервалов от количества/перечня стеков

Результат: система показывает предложенные даты выбранных КТ.

### 4.4. Редактирование предложенных дат

Пользователь может отредактировать предложенные даты КТ вручную. Изменения сохраняются в релизе.

### 4.5. Учет прохождения контрольных точек (ручной)

Для каждой КТ:
- отметить пройдена / не пройдена (статус)
- указать дату и время прохождения
- при задержке указать комментарий с причиной (обязателен при фиксации просрочки/задержки)

## 5. Отчетность и аналитика

### 5.1. Отчет по незавершенным релизам (шаблон статусного сообщения)
- кратко, структурировано, с текущими статусами
- пригодно для отправки в чат/почту

### 5.2. Подробный лог релиза
- перечень КТ
- плановые даты
- фактические даты/время
- комментарии причин задержек
- история изменений (если предусмотрена)

### 5.3. Аналитика для ретро (с фильтрацией)
- фильтры: период, статус, тип КТ, задержки, стеки и т.п.
- форматированный вывод: таблицы/карточки/сводки
- фокус: узкие места и причины задержек

## 6. Требования к интерфейсу (UI/UX)

- простой дизайн
- компонентный подход (контейнеры/компоненты)

Минимальные экраны:
- список релизов
- создание/редактирование релиза
- карточка релиза с КТ (план/факт, статусы, комментарии)
- отчеты/аналитика

## 7. Требования к хранению данных

Допускаются варианты:
- только фронтенд (локально)
- простой backend + БД (**выбран вариант**: Next.js API + Postgres)

## 8. Требования к развертыванию

- база данных всегда поднята (постоянно доступна)
- фронт быстро деплоится через Vercel

## 9. Ограничения и допущения

- учет прохождения КТ — ручной
- расчет дат — предложение, которое можно редактировать
- интервалы этапов и календарь рабочих дней доступны системе как настройки/конфигурация

## Реализовано

### Этап 0 — технический фундамент
- Next.js (App Router): UI + API, деплой на Vercel
- Postgres (Neon), `DATABASE_URL`, `/api/health`
- Миграции `001_init`, `002_seed_milestones`
- CRUD релизов, legacy: `milestone_templates`, `release_milestones` (+ API)

### Этап 1 — доменная модель
- Миграция `003`: `release_tasks`, `stacks`, `release_stacks`
- Миграция `004`: флаги `flag_int`, `flag_psy`, `flag_nt`
- Миграция `005`: `release_stages` (основное хранение этапов)
- Миграция `006`: `release_date` nullable до первого сохранения плана
- UI: задачи и стеки на карточке (`ReleaseInputsClient`)
- `docs/06_DOMAIN_RULES.md`

### Расчёт дат этапов (ядро «Этапа 2» по смыслу ТЗ)
- Конфиг цепочки и сдвигов: `src/config/scheduling.ts`
- Калькулятор: `src/services/scheduling/` (forward/backward, техокна, нормализация выходных при backward)
- API: `POST …/schedule/preview`, `POST …/schedule/apply`
- UI: блок планирования (`ReleasePlanningClient`) + таблица этапов (`ReleaseStagesClient`)
- Документация: `docs/07_SCHEDULING_LOGIC.md`
- Поля: `suggested_at` (расчёт) и `planned_at` (ручная правка)

### Статус-отчёт для чата (ТЗ §5.1) — **сделано**
- `src/services/reports/` — генерация текста, эмодзи этапов, выравнивание колонок
- `GET /api/reports/status-message` → `text` + `telegramText` (блок ``` для Telegram)
- UI `/reports`: превью, «Копировать в Telegram», легенда эмодзи
- `RELEASE_COMPOSITION_URL` — ссылка «СОСТАВ РЕЛИЗОВ» в футере
- Шаблон и правила: `docs/05_REPORT_TEMPLATES.md` §1

### Прочее (вне нумерации этапов)
- Светлая тема UI, читаемый текст в полях ввода
- `release_date` выставляется при apply из даты этапа ZNI_DONE

## Не реализовано или частично

| Область | Заметка |
|---------|---------|
| Лог релиза (ТЗ 5.2) | Данные в БД есть; сводного просмотра/экспорта нет |
| Аналитика ретро (ТЗ 5.3) | Нет фильтров, агрегаций, CSV |
| Часы задач и стеки в формулах (ТЗ 4.3) | Ввод есть, на `offsetDaysFromPrev` не влияют |
| Выбор состава КТ (ТЗ 4.2) | Все этапы цепочки всегда; нельзя «снять» лишние |
| Календарь исключений (праздники) | Только Пн–Пт + правила техокон в коде |
| Статусы релиза draft → active → done | Поле в БД; UI переключения и мастера нет |
| Визуализация просрочек на карточке | Правило в домене; подсветки/бейджей нет |
| Аудит изменений | Нет `audit_events` |
| Auth / роли | Нет |
| Admin UI справочников | Нет |
| Unit/e2e тесты калькулятора | Нет |
| Legacy `release_milestones` | API и клиент остались; основной поток — `release_stages` |

## План будущих работ (приоритет)

### Приоритет 1 — отчётность (этапы 8–9)

**Статус-отчёт (§5.1) — выполнен.** Дальше: лог релиза и аналитика.

1. **Лог релиза** (§2)  
   - Экран или модал на карточке: все этапы, planned/suggested/actual, delay, дельта к плану

3. **Аналитика (минимум)** (§3)  
   - Фильтры: период, статус релиза, этап, «была задержка»  
   - Таблица + экспорт CSV

Зависимости: достаточно текущей схемы `release_stages`; уточнить в коде сравнение для просрочки: `actual_at` vs `planned_at`.

### Приоритет 2 — довести планирование до ТЗ (этапы 3–4, доработка 6)

1. **Влияние `taskHours` и стеков** на сдвиги (коэффициенты в конфиге или `estimation_rules`)  
2. **Опционально:** календарь исключений (праздники) — конфиг или таблица `team_calendar`  
3. **Карточка релиза:** подсветка просроченных этапов, «следующая КТ»  
4. **Unit-тесты** для `calcSchedule` (forward, backward, техокна, выходные)

### Приоритет 3 — UX и жизненный цикл (этапы 5–6)

1. **Мастер создания релиза:** данные → задачи/стеки/флаги → расчёт → правка → сохранить → `active`  
2. **Черновик:** явный `draft`, возврат к редактированию плана без путаницы с «боевым» релизом  
3. **Выбор этапов** (если нужен по ТЗ): отключаемые этапы вне цепочки или урезанные пресеты — согласовать с бизнес-правилами

### Приоритет 4 — инфраструктура данных (этап 2, 7)

1. **Audit log** по apply плана, смене planned/status, reason  
2. **Admin UI** (опционально): стеки, календарь, версии правил расчёта  
3. **Уборка legacy:** deprecate `release_milestones` в UI/docs или удалить после миграции данных

### Опционально (этапы 10–11)

- Auth, привязка действий к пользователю  
- E2E smoke для демо/защиты  
- Демо-сценарий: создать релиз → рассчитать → отметить этап → отчёт
